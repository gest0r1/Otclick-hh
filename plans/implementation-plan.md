## Что берем из hh-auto

### 1. Разделение фонового поиска и пользовательской работы

В `hh-auto` `BacklogWorker` только ищет/фильтрует/скорит вакансии и складывает их в долговечную очередь. Пользовательская работа вынесена в `BatchManager`, который берет уже оцененные вакансии и дает их на выбор.

Для Otclick сохраняем принцип:

`поиск -> сохранение -> скоринг -> ручной просмотр -> выбор -> письмо -> утверждение -> очередь отправки -> отправка`

Поиск и скоринг не имеют права сами отправлять отклик.

### 2. Долговечная state machine

В `hh-auto` очередь хранит lifecycle вакансии и переживает перезапуск. В Otclick не копируем JSON-файл: используем уже существующий PostgreSQL/Supabase.

Нужные состояния первой версии:

- `discovered`
- `scoring`
- `scored`
- `review`
- `selected`
- `letter_draft`
- `approved`
- `queued_to_send`
- `sending`
- `sent`
- `rejected_by_user`
- `hold`
- `archived`
- `score_error`
- `send_error`

### 3. Ручной выбор перед отправкой

Из `hh-auto` берем пользовательскую модель Batch:

- показать набор найденных вакансий;
- пользователь выбирает интересные;
- неинтересные можно отклонить с причиной;
- только выбранные идут дальше.

В Otclick это будет не временный JSON batch, а представление над постоянной БД.

### 4. Последовательная очередь отправки

`hh-auto` реально обрабатывает вакансии последовательно, но Playwright-loop намеренно делает паузу 15–25 секунд на «чтение» вакансии и дополнительно проходит DOM формы. Это одна из причин медленной отправки.

В Otclick:

- оставить строго последовательную отправку для одного HH-аккаунта;
- использовать существующий web-session/form_filler механизм Otclick;
- не переносить искусственную паузу 15–25 секунд;
- ввести небольшой настраиваемый safety interval между откликами только если он нужен для стабильности HH;
- один worker/lock на HH-аккаунт;
- повторный запуск и двойной клик не создают второй отклик.

### 5. Сопроводительные письма

Из `hh-auto` переносим не весь LLM-стек, а проверенные принципы генерации:

- scoring и письмо — разные вызовы;
- письмо создается только для выбранной вакансии;
- полное описание вакансии передается в генератор;
- язык письма совпадает с языком вакансии;
- только подтвержденные факты кандидата;
- открытие письма — конкретный релевантный кейс/результат, а не универсальное приветствие;
- 1–2 доказательства из опыта;
- финальная фраза специфична именно для этой роли/работодателя;
- ориентир по длине: 500–750 символов;
- контекст скоринга может подсказывать, какой кейс релевантнее, но оценка/сомнения не должны попадать в текст письма;
- кэш письма должен учитывать vacancy + resume/profile version + facts version;
- редактирование письма пользователем сбрасывает прежнее утверждение.

Статический fallback после сбоя LLM автоматически не отправляется.

Отдельная постоянная `application_send_queue` (или эквивалент), а не `asyncio.Queue`.

- [ ] Возможность выбрать несколько вакансий и нажать `Отправить выбранные`.
- [ ] Worker берет по одной записи строго последовательно.
- [ ] Per-HH-account lock не допускает параллельных submit.
- [ ] Перед каждым submit: проверить, что вакансия существует и отклика еще нет.
- [ ] После network uncertainty сначала сверить HH, затем решать о retry.
- [ ] Idempotency key/unique constraint для vacancy+resume.
- [ ] Не блокировать работодателя целиком из-за одного предыдущего отклика.
- [ ] Анкеты/неизвестные обязательные вопросы переводить в manual review.
- [ ] Настраиваемый safety interval между откликами без обязательных 15–25 секунд hh-auto.
- [ ] UI прогресса очереди: `N из M`, текущая вакансия, отправлено/ошибка/требует действий.
- [ ] Pause/Resume/Stop после текущей вакансии.

**Приемка:** выбранные вакансии отправляются по очереди существенно быстрее hh-auto, но без параллельных откликов и дублей.

# Архитектурный принцип первой версии

Не переносить `hh-auto` целиком и не заменять Otclick его Playwright-архитектурой.

Используем лучшее из двух проектов:

- **Otclick:** web-session HH, FastAPI + PostgreSQL/Supabase, существующая авторизация, формы/анкеты, Docker stack, mobile-capable frontend.
- **hh-auto:** разделение background discovery и user batch, lifecycle queue, последовательная обработка, проверенный подход к personalized cover letters.

Целевой поток:

`HH sources -> PostgreSQL vacancy pipeline -> hard filter -> LLM score -> mobile review -> selected -> personalized draft -> user approval -> persistent send queue -> sequential Otclick submit -> HH verification -> application log`
